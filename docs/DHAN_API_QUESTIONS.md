# Questions for Dhan API Team

This document lists open questions and observed differences between **official DhanHQ API v2 documentation** and **live API responses** from Phase 1 validation (11-Aug-2026).

We are building a read-only holdings tracker that syncs Trade History daily via TOTP authentication (GitHub Actions). Your answers will help us implement idempotent ingestion and reliable lot accounting.

**References we use:**

- https://docs.dhanhq.co/api/v2/
- https://dhanhq.co/docs/v2/
- Local export: `dhan-api-docs.md` (in this repo)

## 1. Trade History — `exchangeTradeId` always `"0"`

### What docs say

Trade History includes `exchangeTradeId` described as:

> *"Trade specific identification generated by exchange"*

Documentation examples show non-zero values (e.g. `"407958"`).

### What we observed

In a live `GET /v2/trades/{from-date}/{to-date}/0` response (19 trades, NSE_EQ CNC), **every row** had:

```json
"exchangeTradeId": "0"
```

### Questions

1. Is `"0"` expected for certain segments, product types, or order types?
2. Under what conditions is a real exchange trade ID populated?
3. For idempotent trade ingestion, what field(s) do you recommend as a **stable unique key** per trade row when `exchangeTradeId` is `"0"`?
4. Is a composite key acceptable on our side (e.g. `orderId` + `exchangeTime` + `tradedQuantity` + `tradedPrice` + `transactionType` + `isin`)?

**Our implementation:** composite key includes `isin` — required after observing IPO rows with `orderId`/`securityId` = `"0"`. See [`OBSERVATIONS.md`](OBSERVATIONS.md).

## 2. Trade History — `orderId` vs multiple fills (partial execution)

### What docs say

`GET /v2/trades/{order-id}` documentation states:

> *"Often during partial trades… The response of this API will include **all the trades generated for a particular order id**."*

This implies one `orderId` can map to **multiple** Trade History rows.

### What we observed

In our 30-day sample, each `orderId` appeared once (19 rows, 19 unique `orderId` values). We have not yet seen a partial-fill split in our account data.

### Questions

1. Can Trade History return **multiple rows with the same `orderId`** for a single partially-filled order?
2. If yes, is `exchangeTradeId` (when non-zero) the correct unique identifier per fill?
3. If `exchangeTradeId` is `"0"`, how should clients distinguish multiple fills for the same order?

## 3. Trade History — date/time format (`exchangeTime`)

### What docs say

Documentation examples show formats like:

```text
"exchangeTime": "2022-12-30 10:00:46"
```

### What we observed

Live data uses ISO-8601 with `T` separator:

```text
"exchangeTime": "2026-08-10T10:17:36"
```

Also observed: multiple trades sharing the same `exchangeTime` (e.g. two BUY orders at `2026-08-07T15:00:01`).

### Questions

1. Which format is canonical — space-separated, ISO with `T`, or both?
2. Will the format change, or should clients accept both?
3. What timezone is `exchangeTime` in (IST)?

## 5. Trade History — pagination

### What docs say

- Endpoint: `GET /v2/trades/{from-date}/{to-date}/{page-number}`
- Page number starts at `0`
- Response is paginated

Docs do not clearly document page size, a `hasMore` flag, or exact termination rules.

### What we observed

- Page `0` returned 19 trades; page `1` would return empty (loop stops on empty array)
- We used: **keep fetching until response is an empty list**

### Questions

1. What is the maximum number of trades per page?
2. Is empty array the correct termination signal?
3. Is there a documented maximum date range per request?
4. How far back does Trade History allow retrieval (months/years)? Any account-level limits?

## 6. TOTP authentication — automation and token lifecycle

### Our use case

We plan to run a **daily automated job** (GitHub Actions) that:

1. Reads `DHAN_TOTP_SECRET` from secure storage
2. Generates current TOTP programmatically
3. Calls `POST https://auth.dhan.co/app/generateAccessToken`
4. Uses the token for read-only APIs (Profile, Holdings, Trade History)
5. Discards the token when the job finishes

We do **not** store or reuse tokens between runs.

### What docs say

- TOTP endpoint returns `accessToken` + `expiryTime` (~24 hours)
- API Key & Secret credentials last 12 months, but require browser login for each token
- `RenewToken` extends an **active** web-generated token by 24 hours

### Questions

1. Is programmatic TOTP → `generateAccessToken` **officially supported** for unattended daily automation?
2. If we call `generateAccessToken` twice while both tokens are still within their 24h validity:
   - Do both tokens remain valid?
   - Or does the new token invalidate the previous one?
3. Is there a rate limit on `generateAccessToken` calls per day?
4. Any restrictions on calling from cloud CI IPs (e.g. GitHub Actions runners)?
5. For long-running unattended jobs, is TOTP the **recommended** auth method vs API Key + Secret + browser consent?

## 7. Holdings API — reconciliation fields

### What we observed

Holdings response includes: `tradingSymbol`, `securityId`, `isin`, `totalQty`, `dpQty`, `t1Qty`, `availableQty`, `avgCostPrice`, etc.

Some rows show `dpQty: 0` with `t1Qty > 0` (T+1 settlement after BUY).

**T+1 after SELL (11-Aug-2026):** MVELECTRO (`INE0OWZ01020`) — SELL placed ~2:30 PM on 11 Aug. Holdings snapshot same night still showed `totalQty: 32` but `dpQty: 0`, `t1Qty: 0`, `availableQty: 0`. Trade History showed the SELL by 12 Aug noon. Holdings may lag until settlement completes. Full detail: [`OBSERVATIONS.md`](OBSERVATIONS.md) §2.

### Field definitions (from Dhan docs)

| Field | Documented meaning |
|-------|-------------------|
| `totalQty` | T1 qty + delivered qty |
| `dpQty` | Delivered quantity (in demat) |
| `t1Qty` | T+1 quantity |
| `availableQty` | Total quantity minus pledged quantity |

### Our working hypothesis (until Dhan confirms)

For Phase 3 reconciliation (FIFO open qty vs Holdings), compare against **`availableQty`** — not `totalQty`. Rationale: after a SELL, `totalQty` can still show the stock while `availableQty` may already reflect zero tradable qty.

Alternative considered: `dpQty` (settled/delivered only) — also reasonable; awaiting Dhan guidance.

### Questions for Dhan

1. For reconciliation of open demat holdings vs trade-book FIFO, which field is authoritative: **`totalQty`**, **`dpQty`**, or **`availableQty`**?
2. After a CNC SELL on day T, when does each qty field update (same day, T+1, T+2)?
3. How should **`t1Qty`** be treated when computing open lots for tax holding-period tracking?
4. Can `totalQty > 0` while `dpQty`, `t1Qty`, and `availableQty` are all zero (as observed for MVELECTRO post-SELL)? What does that state mean?
5. Does FIFO cost basis from Trade History align with `avgCostPrice` in Holdings, or can they diverge?
